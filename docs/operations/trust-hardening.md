# 企业试用前的可信性加固交接

## 当前状态

下文保留此前加固审计的改动与当时测量结果，不代表最新安装包或线上状态。
这些修复与后续 Codex 配置解析已整理进 0.6.0，版本清单同步，
安装包验收流程见[发布清单](publish-checklist.md)，实际公开验收见[发布记录](https://github.com/ciceroyang/agentgate/releases/tag/v0.6.0)；不能因为源码已有修复就说部署已经更新。
本地验收结果不能转述成线上已修复，也不能转述成已有企业采用、收入或投资进展。
本轮使用隔离测试材料，没有采集客户清单、运行客户项目或联系客户。

业务目标是获得首个企业用户，逐渐形成可盈利的交付，再以客户事实建立融资依据。
因此先修会影响客户判断和信任的问题，不用目录收录量、命令数量或测试通过替代客户价值。
商业阶段与工程里程碑分开，见 [路线图](../roadmap.md)。

## 已落地的本地改动

| 审计项 | 改动 | 如何复核 |
| --- | --- | --- |
| A：必需证据未读仍通过 | 缺索引或无精确匹配记录返回不完整；显式错误或样本索引报输入错误；Action 支持传索引 | 专项回归的缺证据与 CLI 负例 |
| B：策略收紧反而放行 | 全部必需组件与整体执行先检查，再追加指定扫描器；验证输出与计数一致性 | 策略单调性、输出缺失与计数冲突负例 |
| C：旧缓存伪装新证据 | 清单缓存绑定路径、分支、仓库更新时间和读取器代码；审查缓存绑定包坐标、材料摘要与审查代码；保留真实观测/审查时间 | 真实采集脚本在模拟响应下验证缓存命中与失效 |
| D：TOML 身份跨表拼接 | 只读明确支持的项目表；重复、动态或不支持的字段保持未知 | Python、Poetry、Cargo 隔离材料 |
| E：风险变化被漏报 | 比较发现内容、严重度、材料与扫描器指纹；区分生态和同名多版本；不在归档新增风险原文 | 同数量风险升级、内容改变、扫描器改变和输入重排 |
| F：发现到清单丢身份 | 按实际包身份去重；同名冲突保留并提示；文本保留生态；新增 inventory JSON 导出 | PyPI 往返、别名冲突与客户流程回归 |
| G：批量审计遗漏与参数泄漏 | 允许批次逐项记录；整批拒绝记录各项实际拒绝；启动横幅不回显命令参数 | 网关批次测试与合成敏感参数测试 |
| H：撤回版本误认 | 使用声明版本的发布文件，区分部分与全部文件撤回 | 声明版与最新版状态相反的负例 |
| I：钩子错误归因 | 每个安装钩子只关联自己的文件引用 | 无害钩子与安装脚本分离的负例 |
| J：样本替换正式站点 | 采集失败停止 Pages 发布；样本显著标识；差异展示要求与索引字节绑定；试用页指向同站数据 | 静态站构建与样本/差异测试 |
| K：子路径链接失效 | 构建支持部署前缀；记录详情、证据包入口和静态导航同时适配 | 根路径与项目子路径构建测试 |
| L：证明能力被夸大 | 历史页和证据包规范只声明内部一致性，不声明真实时间或整链不可重写 | 文案、规范与页面生成检查 |

另行收紧了空执行、空归档与无实际决策日志的“已测到”判断；默认测试包含发布模块，
测试/发布工作流加入本地打包内容检查；帮助参数不再启动采集。
证据包沿用来源观测时间，不以生成报告的时间填补缺失记录。

复现入口：`test/trust-regressions.test.mjs`、对应模块测试及 `scripts/verify.sh`。
完整流程回归通过隔离材料走完发现、策略、变化归档、证据包与校验，并验证修改文件会被发现。
这是流程回归，不是实际客户环境的验收。

## 升级与发布必须分开处理

具体迁移说明见 [0.6.0 升级指南](upgrade.md#060)。

- 发现结果的纯文本格式改变；来源与冲突诊断保留在完整 JSON，导入清单的 JSON 只保留身份字段。
- 老 watch 投影升级后的首次捕获可能显示基线身份变化；保留旧归档，不回写旧哈希，也不把迁移当成风险升级。
- 老缓存需要重新观测。普通索引重建和 `agentgate refresh` 不会自动执行清单读取与包审查阶段。
  批准采集后，先更新仓库元数据和分类，再运行清单读取与包审查，最后用该结果重建索引。
- 仓库缓存中的修订线索来自已收集的更新时间和分支，不是不可变提交证明；上游元数据也需要更新。
  材料摘要只说明实际读到的字节，不保证工作区安装内容与它相同。
- 发布前按兼容规则确定新版本、走发布验收；上线后再从公开入口复核安装包、页面、数据时间和回滚能力。
  本轮没有提前执行这些外部动作。

## 仍然不能承诺的能力

- 没有对生产记录重新采集和重审，因此没有给出“线上受影响记录全部修复”的数量或结论。
- 只检查已列材料；不等于执行了仓库源码、覆盖全部传递依赖或验证了实际运行时安全。
  仓库记录仍可因源码未检查而不完整，这不是应消除的显示问题。
- TOML 解析是保守子集；Maven 等其他格式没有在本轮扩展为完整解析器。
- 网关日志不是经过签名的完整审计账本，也没有把上下文日志逐条绑定到全部清单工具。
  日志写入失败的运行时策略、完整调用覆盖仍需企业试用前专门评估。
- 哈希链、文件清单与封条可以校验内部一致性；整份材料连同哈希一起重建不能靠自校验识别。
- 完整发现报告可能包含配置位置或内部名称，需本地留存并在分享前脱敏。
- 未验证真实浏览器点击与弱网/移动端体验，未完成大索引按需加载；静态页面测试不能替代体验验收。
- SSO、角色权限、多租户、托管计费和服务保证没有因本轮加固而实现；不能作为现有销售承诺。

## 面向首个企业用户的下一步

优先验证的买方假设：正在部署 MCP 工具、需要回答“用了什么、检查到了什么、缺什么证据、
升级后变化了什么”的 AI 产品或平台团队，尤其是正在做工具审查或客户安全问卷的团队。
这是假设，不是已确认的客户画像；没有凭此编造联系人、需求、采购时间或预算。

试点开始前，由用户选定并授权接触对象，确认实际使用者、决策人、工具范围、材料边界与评审任务。
沿用已有 [试点方案](pilot-package.md) 作为提案，不把文档价格当成市场已经接受的价格。

试点要留下的结果是：客户能独立完成清单与报告，指出漏项/误报，依据报告作出真实决定，
在实际工具变更后愿意再次使用，并明确是否愿意购买哪项交付。
记录支持与交付投入、运行成本和实际付款，才能讨论盈利；记录持续采用与可重复成交，
才有融资材料。没有这些事实时，应调整买方或场景，而不是持续堆企业功能。

本轮不发送销售消息、不承诺免费额度或新报价、不签服务保证；这些动作需要明确对象与授权。
